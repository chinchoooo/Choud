Storage: content-addressed, crash-safe, verified

  1. Name by content. A file is stored at objects/<first two hex>/<sha256>. Same bytes under any name: one copy. Reference counting lives in PostgreSQL: an object is deleted only when nothing references it, by a trash purge or the opt-in garbage collector.
  2. Write aside, flush, rename. Bytes go to a unique temporary name, are flushed to the disk, renamed into place, and the folder entry is flushed. A power cut leaves the old state or the complete new one, never half.
  3. Verify before trusting. A put re-hashes the source before moving it (a wrong hash is refused and the source is left alone), and a get re-hashes the stored bytes, so silent disk damage is caught instead of served.
  4. Confine paths. The engine resolves every path (.. and symlinks included) and refuses anything outside the storage root, and anything inside objects/ unless it is a read.

How it is tested

  • 91 engine tests. They include forked processes killed (_exit) at named points mid-write, simulated full-disk failures, and 16 writers of the same object at once.
  • Sanitizers. The engine suite also passes under AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer.
  • Fuzzing. A libFuzzer target feeds the JSON parser and path confinement; 660,000 executions ran clean.
  • 384 server tests on SQLite by default, and the whole suite can run against a real PostgreSQL (TEST_DATABASE_URL), using a fake engine that mirrors the real one.

The engine's request parser is a strict flat-object JSON reader (it rejects nesting, duplicate keys, bad escapes and trailing garbage). It handles up to 32 connections at once with a read timeout. docs/storage.md

What changed between the two Choud columns

  • The two upload endpoints were async but made blocking engine and database calls, so one upload waiting on the disk stalled every other request. The blocking work now runs in worker threads.
  • Clients send up to three 5 MiB chunks at once.
  • The engine no longer reads an uploaded file twice (the backend tells it the engine just hashed it).
  • Downloads use a hard link into staging instead of a full copy.

The 5 GB download came out slower on the second run with nothing slower in its path: one run each, so it is most likely noise, and it is reported rather than hidden.

Security model

  • Two doors. The private door serves the app and the API. A second door serves only /s/* share links, and a header it stamps is stripped on the private door. A kill switch pauses every public link at once.
  • Passwords and tokens. Argon2id hashes, short-lived access tokens with refresh tokens, optional TOTP two-factor login. The share-unlock cookie is signed with a key derived (HKDF) from the JWT secret, never the secret itself.
  • Rate limits on login, registration, refresh, uploads, downloads, search, thumbnails, share views and unlock attempts, per client IP.
  • Request guards. A body-size limit (413 before the body is read), security headers, no-store on auth responses, and CORS off unless you list origins.
  • Vault. Sealed in the browser: the server stores ciphertext, and still sees how many sealed files there are, their sizes and dates.
  • Secrets. scripts/setup.sh generates strong random ones; production refuses to start with placeholders.

What it has not had

  • No independent security audit.
  • No weeks of use on many real phones.
  • No multi-machine or multi-tenant hardening: it is built for one household on one machine.

Questions

Will it run on Windows or a Mac?

To try it, yes: make dev with Docker Desktop. To keep your files, use Linux: Docker Desktop's virtual disk makes every write slow.

Can I reach it away from home?

Over Tailscale. Public share links work from anywhere with scripts/enable-public-links.sh, through the second door.

What if the disk dies?

Nightly verified backups with restore scripts. Point them at a second disk or machine.

Can I import from Google Drive?

No importer yet. Export with Google Takeout and upload the folder.
